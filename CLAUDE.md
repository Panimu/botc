# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Blood on the Clocktower personality quiz covering every character (all 181 roles, including travellers, fabled and loric). The player answers binary questions; each answer **strictly eliminates** every character on the losing side, and the next question is picked **at random, weighted towards even splits** of the remaining pool, and (while more than 15 remain) towards splits that seat the town circle with 7–15 characters (`CIRCLE_TARGET` in `js/engine.js`, shared with `js/circle.js`) (`SPLIT_WEIGHTING` in `js/engine.js`: entropy of the split ^1.5 plus a small floor, so narrow questions stay possible and come naturally late in a game). Uniform selection made 55% of opening questions single out one character. The game ends when one character is left. Questions are authored by Claude Code, following `data/questions/GUIDE.md` (format, accuracy rules, and the voice cast for the styled lines). Each question has a `plain` phrasing (shown in the daily hunt) and a `styled` phrasing (shown in the personality quiz) written in the manner of a character from Matt Dinniman's books, recorded in `voice`. **Those names must never reach the browser**: `voice` is stripped at publish time, no visible text may name them, and `scripts/build-site.js` fails the build if one appears.

Live at https://botc.panimu.com/ (Mythic Beasts static hosting, Apache): the home page (`index.html`) is the daily hunt, `quiz.html` is the personality quiz, and `daily.html` redirects old hunt links to the home page. `og:url`/`og:image` point there. It is uploaded by hand, a release at a time: `npm run upload` validates, tests, builds `_site/` stamped with the commit id, and copies into `upload/` (which nothing else touches) only the files that changed since the last confirmed upload; push `upload/`'s contents into the web root, overwriting, then run `npm run uploaded`, which records that version as live and empties `upload/`. What the server has is kept in `.cache/upload-state.json` (`scripts/upload-state.js`); files are compared with the version stamp taken out, but when anything changed, every stamped file (pages, scripts, `sw.js`) goes up too so they all carry the new stamp. Files removed from the site are listed for deleting by hand. `npm run upload -- --all` prepares everything, for a fresh web root (include the hidden `.htaccess`). Share pages stamp their preview image with the card's own hash, so they only change when the card does. **Never upload the repo root**: it exposes the `voice` names, `CLAUDE.md`, the question guide and the build scripts (this happened once, on 2026-10-05). Every push to `main` of github.com/Panimu/botc also runs `.github/workflows/pages.yml`, which validates, tests, stamps asset URLs and deploys a mirror to https://panimu.github.io/botc/.

**Cache-busting:** Pages caches files for 10 minutes, and a browser that mixes a new `index.html` with an old cached script breaks. So every reference to our own JS, CSS and JSON carries `?v=dev` (in `index.html`, `import` lines and `fetch` calls), and the workflow replaces it with the commit id. Add the marker to any new asset reference, including new module imports. `build-site.js --version` does the same for the Mythic Beasts upload.

## Commands

- `npm run serve`: builds `_site` and serves it at http://localhost:8000. You can also serve the repo root directly (`python -m http.server`); it works the same, except that source data still carries `voice`.
- `npm run build`: `scripts/build-site.js` builds the publishable `_site/`: only the site's own files, `voice` stripped, `?v=dev` stamped (with `--version`), and a scan that fails on any banned name. It also writes `sw.js` with the version and the precache list (`precacheList()`: pages, every script, CSS, game data, icons, generic art), so the site starts offline. In the source `sw.js` the list is empty, so serving the repo root precaches nothing. The deploy publishes `_site/`.
- `npm test`: Node's built-in test runner (`node --test`). Single test: `node --test --test-name-pattern="undo" test/`.
- `node scripts/print-splits.js <file>.json` (or `--id <id> …`): prints questions with their yes and no sides resolved to character names, for reviewing splits.
- `npm run validate`: data integrity, art presence, separability coverage, and simulated games. `--verbose` lists every unseparated pair. Run after every change to `data/`.
- `npm run editor`: a local editor at http://localhost:8010 (`tools/editor/`, listens on 127.0.0.1 only, never published). **Questions**: search and filter, create, duplicate, rename (warns: renaming resets hunts in progress that asked it), delete, edit wording, voice and answer labels with live hunt/quiz previews, and change the split by clicking characters (yes side or scope, undo/redo, set from pasted names, same-split detection). **Review**: a list of questions to check, each with its reasons (text, source, date), a reviewed tick and a note of what was decided. It lives in `.cache/review-queue.json` (not committed), so agents can add to it too (`scripts/queue-review.js`): `{ items: [{ id, reasons: [{ text, source, added }], reviewed, resolution, rev }] }`. The page never posts the whole list: it sends one change at a time (`/api/review/add`, `/update`, `/remove`), which the server applies to the file as it is now. `rev` counts an entry's changes; an update or removal carrying an older `rev` is refused, so a stale page can't overwrite newer additions. Anything else writing the file should bump `rev` when it changes an entry. Renaming or deleting a question updates its entry. Pasting text adds each line's question id, with the rest of the line as its reason. **Characters**: one character's traits (yes/no/unclear) and share quote in one place. **Traits**: edit, create or delete (only if unused) traits. Question saves are checked with the validator's rules; trait and character saves are checked with the validator's trait rules (`traitProblems`) before anything is written, then rerun `build-characters.js` and report any question they break; quotes are checked for banned names and em dashes.
- `node scripts/build-characters.js`: regenerates `data/characters.json` from `resources/data/`. Don't hand-edit that file.
- `python scripts/make-share-cards.py`: regenerates the quiz's per-character link-preview cards in `resources/og/characters/` (needs Pillow). Rerun after adding characters or changing token art. The build turns them into share pages, `you/<id>.html`: each carries the character's preview tags and forwards visitors to the quiz. The quiz's share link points there, left bare so Discord expands it.

There are no dependencies. The site runs from the source files; the build only prepares the published copy.

## Architecture

- `resources/`: reference material supplied by the user and published with the site: `data/roles.json` (all roles with official ability text), `nightsheet.json` (night order), `jinxes.json`, and token art in `characters/<edition>/<id>[_g|_e].webp` (fabled/loric have no suffix; `generic/<team>.webp` is the fallback).
- `data/characters.json`: generated. Per character: `id`, `name`, `team`, `edition`, `summary` (the official ability), `image`, plus boolean fact flags (`firstNight`, `otherNight`, `setup`, and regex-derived ones like `oncePerGame`, `startsKnowing`, `madness`). Add a flag in `ABILITY_FLAGS` in the build script to make it selectable.
- `data/questions/*.json`: one file per character group, all listed in `data/questions/index.json`, which the app and validator load. Each question is `{ id, plain, styled, voice, yes, scope?, options? }`. `yes` and `scope` are selectors: an id list, or a match object on character fields (`{ "team": ["minion", "demon"] }`, `{ "otherNight": true }`). **Without `scope`** the question is global and everyone else is on the "no" side. **With `scope`** it's only asked when the whole remaining pool is inside the scope, so its wording can presuppose that context. Note that `firstNight`/`otherNight` mean "on the Storyteller's night sheet", not "wakes".
- `data/traits/*.json`: hand-tagged, wiki-reviewed cross-team traits (`killsAtNight`, `learnsAlignment`, `psyPatient`, `iconShowsAnimal`…), each with a definition and a `yes` list. Subjective ones also carry a `no` list, and the build adds a `<trait>Clear` field so questions can scope out borderline characters. `build-characters.js` merges traits into `characters.json`, so rerun it after any trait edit. Prefer traits over id lists and over the crude regex flags (see "Known traps" in `data/questions/GUIDE.md`).
- `.claude/agents/question-reviewer.md`: the wiki review agent. Run it on any new or edited question file. Its wiki notes are cached in `.cache/wiki/` (gitignored), and icon contact sheets are in `.cache/icons/`.
- `js/engine.js`: pure game logic (`Game`, `select`, `prepare`, `splits`), no DOM. Shared by the browser, validator and tests; takes an injectable `rng`.
- `js/daily.js`: the daily hunt's rules, no DOM. A date-seeded schedule picks the character. Offers (`refreshOffers`) are seeded by the date plus the questions asked so far, in order, so every player walks the same tree of options. While more than 15 remain, questions that would leave fewer than 7 (`HUNT_MIN_SIDE`) on either side are set aside, and the three offers aim at 50/50, 60/40 and 70/30 splits (`SPLIT_TARGETS`). At 15 or fewer, questions that would single out one character are set aside. Set-aside questions only fill a slot nothing else can. No two offers split the remaining characters the same way (either way round), even when the questions differ. Offers are shown shuffled. (The personality quiz keeps engine.js's weighting.) `DailyGame` takes the day's `par` (from `parRun`, a greedy solver; computed outside the constructor because par builds a game itself) and enforces budgets: par + 2 questions (`OVER_PAR_QUESTIONS`) and 3 guesses, with guesses beyond 3 spending questions, so a win scores at most par + 5. It's lost when no legal move remains with more than one character left. Without a par it uses the old rules (unlimited questions, three wrong guesses lose), used by the par solver and for replaying hunts saved before budgets. Results store their par, and saved progress freezes it, so tiers (🟦 under par … 🟥 lost, ⬜ missed, ▫️ before budgets) never shift when question data changes par. Streaks count every recorded hunt; a loss or a missed day ends one, and there are no freezes.
- `js/app.js`: DOM rendering: question panel, result panel, and the full list of remaining characters grouped by team inside a collapsible `<details>` (built once, toggled with `hidden`; it's the accessible version of the circle).
- `js/circle.js`: the town circle (decorative, `aria-hidden`). It shows one bead per character, coloured by team (Townsfolk blue, Outsiders teal, Minions orange, Demons red, Travellers brass); eliminated beads go pale. At `SEAT_THRESHOLD` (15) or fewer, survivors animate round the arc into seats as full tokens, and the eliminated stay seated but shrouded. Positions are rotations about the centre so moves follow the ring. Seat art loads on first seating. Animations always play (user decision), including under `prefers-reduced-motion`.
- `scripts/validate.js` checks integrity: both phrasings and a voice, selectors that resolve, yes ⊂ scope, no duplicate ids or text. `node scripts/validate.js <file>.json` checks one file. Run without arguments, it also reports separability coverage and **simulates games**: average length, and how often a game ends **unresolved**. There's no fallback question: when no question splits the remaining characters, the game ends listing all of them. With scoped questions, pairwise separability doesn't guarantee every game resolves, so the simulation is the real measure.

## Constraints

- Static files only: hosted on GitHub Pages and may later move to Mythic Beasts shared hosting (Apache + PHP-FPM + MySQL, no Node). Use relative paths everywhere so it works from the `/botc/` sub-path.
- Accessibility is a requirement, not a polish pass:
  - Keep every text/background pair at WCAG AA or better in both themes (the current palette is mostly AAA).
  - Never convey team by colour alone: team headings and result labels carry it in text.
  - Keep the page usable at 320 CSS px wide with no horizontal scroll.
  - Announce state changes through `#announcer` (an `aria-live` region), and move focus to the question/result heading after undo, restart and the final answer.
  - Themes follow `prefers-color-scheme`, with a manual override stored in `localStorage` under `theme` and applied by an inline script in `<head>`.
- `[hidden]` is forced to `display: none` because component classes set `display`.
